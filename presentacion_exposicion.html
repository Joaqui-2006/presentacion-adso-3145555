Concepto Clave · ¿Cómo debía funcionar el flujo de trabajo?

El Flujo de 3 Pisos en Git: Lo que debía pasar vs. Lo que pasó

En desarrollo de software profesional (Gitflow), el código viaja por 3 estaciones antes de entregarse:

Estación 1 · Rama develop

🛠️ El Taller de Trabajo

Aquí los programadores van uniendo cada Historia de Usuario (HU) día tras día.

Estado en Alerta Mujer:
✅ Lleno con todo el proyecto:
• 62 commits en Backend
• 59 commits en Base de Datos
• 70 commits en Frontend
Estación 2 · Rama qa

🧪 Sala de Pruebas (Calidad)

Cuando el código del taller está listo, se pasa a qa para probar que nada falle.

Estado en Alerta Mujer:
❌ Vacía (0 pases a QA).
Nunca pasaron el código de develop hacia qa. Se quedó en el commit #1 del primer día.
Estación 3 · Rama main

🏆 Vitrina Oficial (Producción)

Es la rama por defecto que abre GitHub, la que revisa el jurado y la que se publica en internet.

Estado en Alerta Mujer:
❌ Vacía (0 entregas en main).
Solo tiene un archivo README.md con una sola línea: el título del repositorio.
🎤
Qué decir en esta diapositiva:

"En un proyecto bien gobernado, el código avanza por tres estaciones: se construye en 'develop', se prueba en 'qa' y se entrega oficialmente en 'main'. El problema de Alerta Mujer fue que hicieron los 191 commits en la primera estación ('develop'), pero jamás movieron el código hacia 'qa' ni hacia 'main'."

Causa Raíz e Impacto · ¿Por qué cometieron este error?

¿Por qué dejaron main vacío y qué consecuencias trajo?

Revisando el repositorio de documentación del propio equipo (AlertaMujer_Docs), encontramos la razón exacta:

🕵️‍♂️ La Causa Raíz (Su propia regla los bloqueó)

  • 1. Se pusieron un candado documental: En su archivo 00-governance/git-conventions.md escribieron:
    "No promover a qa o main sin política aprobada... permanece En refinamiento."
  • 2. Lo dejaron pendiente como GAP-01: En su matriz de trazabilidad reconocieron que nunca cerraron esa política antes de la fecha de entrega.
  • 3. 90 Pull Requests sin revisión de pares (H-16): Hicieron 90 Pull Requests hacia develop, pero todos fueron aprobados por la misma autora en minutos, sin que nadie verificara que main seguía vacío.

💥 Las 3 Consecuencias Graves

  • 1. El repositorio parece vacío al descargarlo: Cualquier evaluador o comando git clone descarga por defecto la rama main y recibe un proyecto en blanco.
  • 2. Imposible desplegar en la nube automáticamente: Plataformas como Vercel, Render o Railway leen por defecto la rama main; al no haber código allí, cualquier despliegue falla.
  • 3. Perdieron la aprobación por 0,6 décimas: Fallar el ítem T-13.9 (*"La rama main contiene el trabajo entregable"*) bajó su nota de Proceso a 50/100 y los dejó en 69,4 / 100 (Juicio D).

La Solución Paso a Paso · Esfuerzo Bajo (S)

¿Cómo se soluciona el problema?

Haz clic en el botón verde para ver cómo cambia el estado de los repositorios al aplicar la solución:

develop
191 Commits listos (62 Backend · 59 Database · 70 Frontend)
✔ 100% Construido
qa
1 commit (Vacío)
❌ Sin integrar (Faltan 191)
main
1 commit (Solo README de 1 línea)
❌ T-13.9 FALLA (69,4 pts)

Paso 1: Pull Request a qa

En los 3 repositorios, crear un Pull Request desde develop hacia qa y ejecutar las 138 pruebas automáticas.

gh pr create --base qa --head develop \
  --title "release: pasar develop a qa"

Paso 2: Pull Request a main

Crear el Pull Request de qa hacia main y pedir 1 revisión aprobada (Approve) antes de darle Merge.

gh pr create --base main --head qa \
  --title "release: entrega oficial en main"

Paso 3: Proteger main

Activar Branch Protection Rules en GitHub y comprobar que no queden commits pendientes:

git rev-list --count main..develop
# Resultado esperado: 0 ✅
Resumen Ejecutivo · Guion Listo para tu Sustentación

Guion Completo en 4 Preguntas (Para cerrar tu exposición)

Si el instructor o tus compañeros te hacen preguntas, aquí tienes las respuestas exactas y directas:

1️⃣ ¿Cuál es el error exactamente?

"En los 3 repositorios técnicos de Alerta Mujer (Backend, Database y Frontend), la rama principal main y la rama qa están vacías: solo tienen el primer commit con un README.md de una línea. Los 191 commits del proyecto quedaron atrapados en la rama develop."

2️⃣ ¿Por qué es un problema grave?

"Porque main es la puerta de entrada oficial de cualquier repositorio. Quien clone el proyecto o intente desplegarlo en un servidor recibe un proyecto vacío. Esto les hizo perder el ítem T-13.9 y quedarse en 69,4 puntos (a 0,6 de aprobar)."

3️⃣ ¿Cómo se soluciona?

"No se debe forzar un push directo. La solución correcta es abrir un Pull Request de develop a qa y luego de qa a main en cada uno de los 3 repositorios, aprobarlo con revisión de un compañero y activar reglas de protección en main."

4️⃣ ¿Cómo sabemos que ya quedó solucionado?

"Se da por cerrado cuando al abrir main en GitHub se ve el código completo, el README.md real y las pruebas, y el comando git rev-list --count origin/main..origin/develop devuelve cero (0) en los tres repositorios."
